## Modern data platforms need an architecture

Modern data platforms do not become valuable simply because data moves from one place to another.

They become valuable when movement, structure, meaning, governance, execution, and evidence follow a coherent architecture.

In this manifesto, architecture means more than a data model.

It means the structural backbone of a data platform:

- how data is ingested  
- how raw information is preserved  
- how technical truth is shaped  
- how business meaning is modeled  
- how serving layers expose trusted data  
- how lineage connects every data object  
- how contracts protect consumers  
- how changes are reviewed  
- how execution is controlled  
- how runtime evidence proves what happened  

This architecture is usually layered.

Not because layers are fashionable, but because responsibilities need boundaries.

A landing or raw layer should not carry business meaning.  
A transformation layer should not become an uncontrolled semantic shortcut.  
A business layer should express rules intentionally.  
A serving layer should make trusted consumption possible without hiding how the result was produced.

A best-practice data platform therefore needs more than pipelines.

It needs an explicit, layered, **reproducible** architecture that can survive technology choices.

The platform may change.  
The SQL dialect may change.  
The orchestration tool may change.  
The architecture should remain understandable.

Platform independence starts here:

with architecture that is defined above tool-specific implementation details.

## SQL is an artifact. Architecture is the contract.

Modern data platforms rarely fail because teams lack tools.

They fail because architecture becomes implicit.

It hides in SQL transformations.  
It hides in orchestration configuration.  
It hides in naming conventions, folder structures, BI models, wiki pages, and the memory of senior engineers.

Sometimes it hides in Python jobs.  
Sometimes it hides in notebooks, templates, orchestration code, or SQL generated by application logic.

At first, this feels manageable.

A team defines a few layers.  
A pipeline framework appears.  
A scheduler starts jobs in the right order.  
A catalog shows which tables exist.  
A semantic layer tries to make business meaning easier to consume.

And for a while, the platform works.

But over time, a quiet shift happens.

Nobody can point to the place where architecture actually lives.

The SQL contains part of it.  
The scheduler contains part of it.  
The catalog observes part of it.  
The BI layer explains part of it.  
The documentation promises part of it.

But the architecture itself is not explicit.

It has to be pieced together later from implementation details.

That is the problem this manifesto addresses.

Modern data platforms need an Architecture Runtime.

---

## Architecture should not disappear inside pipelines

A data pipeline is not the same thing as a data architecture.

A pipeline moves data.

An architecture explains what the platform is, how it is structured, which responsibilities belong to which layer, which dependencies are intentional, which changes are safe, which semantics are governed, and which execution outcomes can be trusted.

When architecture is encoded mainly in SQL and pipeline code, important questions become surprisingly hard to answer:

- Which datasets exist, and why?  
- Which layer owns which responsibility?  
- Which dependencies are intentional?  
- Which columns define the contract?  
- Which transformations express business meaning?  
- Which schema changes are safe?  
- Which changes were reviewed?  
- Which execution was approved?  
- Which runtime evidence proves what actually happened?  

These are not side questions.

They are architecture questions.

If answering them requires reading SQL files, orchestration graphs, BI models, catalog entries, deployment scripts, and old chat messages together, then architecture is not explicit.

It is scattered.

And scattered architecture becomes fragile architecture.

---

## SQL is essential - but it should not be the architecture

SQL is one of the most successful languages in the history of data systems.

It is powerful, expressive, widely understood, and supported by nearly every analytical platform that matters.

SQL is not the enemy.

Nor is this only about handwritten SQL.

In many platforms, architecture also hides in Python jobs, notebooks, templating frameworks, orchestration code, and SQL generated by application logic.

The implementation language changes.

The architectural problem does not.

But SQL should not be the primary place where architecture lives.

When architecture is hidden inside SQL, programming logic, or pipeline code, the platform inherits several structural weaknesses:

- Intent must be inferred from implementation.  
- Governance happens after logic has already been written.  
- Business meaning is mixed with technical transformation.  
- Dialect-specific syntax leaks into modeling decisions.  
- Review focuses on code diffs instead of architecture changes.  
- Execution evidence is separated from architecture intent.  
- Portability becomes difficult because logic and platform syntax are entangled.  

This does not mean SQL is unimportant.

It means SQL should be the output of architecture, not the architecture itself.

SQL should be generated from explicit intent.  
SQL should be reviewable as an artifact.  
SQL should execute in the warehouse.  
SQL should remain visible.

But architecture needs a higher-order representation.

Architecture needs a runtime.

## What is an Architecture Runtime?

An Architecture Runtime is a system that makes architecture executable.

It does not merely document architecture.

It defines, validates, renders, reviews, approves, executes, and records architecture through deterministic runtime artifacts.

An Architecture Runtime treats metadata as operational architecture.

Metadata is not only descriptive.

It defines:

- datasets  
- layers  
- columns  
- keys  
- lineage  
- ownership assignments    
- contracts  
- dependencies  
- architectural patterns  
- business semantics  
- materialization behavior  
- schema evolution intent  
- execution scope  
- review state  
- runtime evidence  

In a complete data architecture, this also includes reusable best-practice mechanisms that should not be reinvented in every pipeline.

Examples include deterministic key generation, structurally equivalent source consolidation, incremental change processing, historization, schema evolution, and controlled serving contracts.

From this metadata, the runtime derives explicit artifacts:

- logical plans  
- dialect-aware SQL  
- architecture state  
- change reports  
- approval artifacts  
- execution previews  
- controlled execution records  
- catalog views  
- portfolio signals  
- audit references  

The runtime does not replace the warehouse.

It does not replace SQL.

It does not replace engineering judgment.

It gives architecture a formal place to live.

## The Architecture Runtime loop

An Architecture Runtime connects definition, discovery, control, execution, and evidence.

A simple runtime loop looks like this:

```text
Metadata-defined architecture
  ↓
Deterministic architecture state
  ↓
Architecture change report
  ↓
Review and approval
  ↓
Execution preview
  ↓
Controlled execution
  ↓
Execution record
  ↓
Discovery and audit evidence
```

This loop matters because architecture is not static.

It changes.

Datasets are renamed.  
Columns are added.  
Business logic evolves.  
Serving contracts mature.  
Execution scopes shift.  
Consumers depend on existing structures.  
Governance requirements increase.

Without a runtime loop, these changes are often handled as implementation details.

With an Architecture Runtime, they become explicit architecture events.

That is the difference between a pipeline that happens to run and an architecture that can be governed.

## Discovery is not control

Data catalogs are valuable.

They help teams find assets, understand ownership, inspect lineage, and improve platform transparency.

But discovery is not control.

A catalog can show that a dataset exists.  
It does not necessarily decide whether an architecture change is safe.

A catalog can show lineage.  
It does not necessarily approve schema evolution.

A catalog can show ownership.  
It does not necessarily enforce execution guardrails.

A catalog can show quality signals.  
It does not necessarily produce runtime evidence.

A scheduler has a different limitation.

A scheduler can start jobs.  
It can enforce order.  
It can retry failures.  
It can show operational status.

But orchestration is not architecture control either.

Starting a job is not the same as proving that the architecture scope was reviewed, approved, still valid, executed under the intended dependency mode, and recorded with deterministic evidence.

Modern data platforms need catalogs.

They need orchestrators.

They need semantic layers.

They need observability.

But they also need a runtime layer that connects architecture definition to controlled execution and audit evidence.

---

## Business semantics should not be an afterthought

Many data platforms treat business meaning as something that appears late.

First, technical layers are built.  
Then transformations grow.  
Then BI models try to make sense of the result.  
Then metric definitions are added.  
Then governance tries to catch up.

This often leads to a fragile split:

Technical logic lives in pipelines.  
Business meaning lives in BI tools.  
Metrics live in a semantic layer.  
Governance lives somewhere else.

The result may work, but it is difficult to reason about.

An Architecture Runtime takes a different view.

Business semantics should be explicit, deterministic, lineage-aware, and executable.

A business concept should not exist only as a query-time abstraction.

A business rule should not be hidden in a dashboard calculation.

A KPI should not be detached from the architecture that produces it.

Business meaning belongs inside the platform architecture.

It can still be consumed by BI tools.  
It can still be exposed through serving layers.  
It can still support semantic layers and applications.

But the meaning itself should be modeled, reviewed, executed, and governed as part of the architecture.

---

## Determinism is not a technical detail

In data platforms, determinism is often treated as a nice engineering property.

For an Architecture Runtime, determinism is more fundamental.

It is a trust requirement.

This is also why the structural backbone of a platform should not be defined probabilistically.

AI can be useful in many places.

It can explain, summarize, assist, suggest, and accelerate.

But architecture needs to be explicit, reproducible, and guaranteed.

AI is based on probability, not certainty.

If every AI-generated result still needs to be validated, debugged, constrained, and corrected, the practical question becomes unavoidable:

Is that really more efficient than maintaining a small amount of explicit metadata and generating architecture reproducibly from it?

The same metadata should produce the same logical plan.  
The same logical plan should produce semantically equivalent SQL for the selected dialect.  
The same architecture state should produce the same fingerprint.  
The same approved change should remain verifiable.  
The same controlled execution should produce an audit record that can be inspected later.

Without determinism, governance becomes subjective.

Without determinism, reviews become fragile.

Without determinism, generated SQL becomes hard to trust.

Without determinism, audit evidence becomes weak.

A runtime that governs architecture must be reproducible by design.

---

## Architecture needs evidence

A modern data platform should be able to answer more than operational questions.

Not only:

```text
Did the job run?
```

But also:

```text
Which architecture scope was executed?
Which architecture state was used?
Which change report was reviewed?
Which approval matched this execution?
Which dependency mode was selected?
Which guardrails were applied?
What happened at runtime?
Which evidence proves it?
```

This is the shift from operational logging to architecture evidence.

Operational logs are still important.

But an Architecture Runtime needs artifacts that bind execution back to architecture intent.

Execution should not be just an event.

It should be evidence.

---

## What an Architecture Runtime is not

An Architecture Runtime is not a data catalog with a nicer interface.

It is not a scheduler.

It is not a BI semantic layer.

It is not a metric store.

It is not a SQL templating framework.

It is not a generic workflow engine.

It is not a dashboard over pipeline metadata.

It is not a replacement for the warehouse.

It is not a replacement for engineering discipline.

An Architecture Runtime is the missing system layer that makes architecture explicit, executable, controllable, and auditable.

It connects the things that are often separated:

```text
Architecture definition
Discovery
Review
Approval
Execution
Evidence
```

That connection is the category.

## elevata as reference implementation

elevata® is an open-source reference implementation of the Architecture Runtime idea for modern data platforms.

It treats metadata as the control plane for data architecture.

It makes architecture:

- explicit  
- deterministic  
- discoverable  
- controllable  
- executable  
- auditable  

In elevata, datasets, lineage, keys, contracts, execution semantics, business meaning, schema evolution intent, review state, and runtime evidence are modeled as part of one architecture system.

SQL remains visible.

But SQL is not the center.

SQL is rendered from structured metadata through logical plans and dialect-aware rendering.

Execution remains warehouse-native.

But execution is not detached from architecture.

Architecture Control makes change intent reviewable, approval state verifiable, execution scope explicit, and runtime outcomes auditable.

Architecture Catalog makes metadata-defined architecture discoverable without turning discovery into execution.

Bizcore makes business meaning explicit and executable without moving semantics into a BI-only abstraction.

Together, these capabilities express one core principle:

```text
Metadata defines architecture.
Architecture Control governs execution.
Execution Records preserve evidence.
SQL remains an artifact.
```

## The platform is not the pipeline

A data platform is not a collection of jobs.

It is not a folder of SQL files.

It is not a scheduler graph.

It is not a catalog inventory.

It is not a semantic layer alone.

A data platform has an architecture that must remain understandable, governable, executable, and trustworthy over time.

That architecture should not live only in conventions.

It should not be reconstructed from implementation details.

It should not depend on memory, discipline, or heroics.

It should be explicit.

It should be deterministic.

It should be reviewable.

It should be executable.

It should leave evidence.

That is why modern data platforms need an Architecture Runtime.

SQL is an artifact.

Architecture is the contract.
